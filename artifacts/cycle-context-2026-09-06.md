## What the existing cycle does

`auto:cycle` optionally updates code, checks environment/browser readiness, arms a capped session, runs `runAutomationSession`, disarms, and writes a cycle report. The worker discovers cards, picks an application, runs the application state machine, and performs post-session outreach and failure triage. Form filling and submission retain approved-plan, capability, verification, duplicate, and confirmation checks.

The current defaults do not quite implement the requested sequence:

- `discoverMax=1` limits cards inspected, not fresh applications queued. `scrapeFeedCardsLive` slices the feed before dedupe/eligibility. An already-known or ineligible top card can consume the entire discovery allocation.
- `pickNextApplication` then chooses the oldest eligible QUEUED application, followed by old in-progress states. It is not restricted to this discovery run. This is why Rivian returned.
- The worker's `runOutreachTail` uses Outlook and one ranked contact. Gmail's insider → generation → draft path is `runOutreachPipeline` / `npm run outreach`. Those are different paths. With one app per cycle, the batch timing is sequential, but the mailbox/provider is still wrong for this request.
- Post-session triage chooses from eight remediation actions. It can requeue or park; it is not a continuously observing application navigator.

## Recommended control loop (proposal; not implemented)

Use the LLM as the navigation decision maker whenever the next step is uncertain. Keep deterministic execution and evidence checks. A continuous model call for every keystroke is unnecessary: maintain a continuous observation/action record, and ask the model at page transitions, ambiguities, and failed postconditions.

1. Read the live feed in its observed order, with a bounded scan. Skip already-known, submitted, excluded, or clearly ineligible entries. Queue at most one fresh eligible posting. If none exists within the scan budget, finish with “no fresh candidate”; never silently substitute the old queue. Queue repair should be an explicit separate run.
2. Maintain one application context: job identity, current URL/tab/frame, screenshot, visible semantic controls, page classification, prior actions and their observed results, relevant error text, candidate-approved values, and remaining budget. Treat page text as untrusted evidence, not instructions. Never provide irrelevant mailbox or credential contents to the model.
3. Use a deterministic fast path for an unambiguous known action, with a named expected result. After each click, refresh context and verify the result. A URL change alone is not “application form reached.” A Workday posting → Apply chooser → Sign In → wizard remains navigation across all those transitions.
4. Ask the LLM immediately when multiple actions are plausible, the page type is unknown, a frame/popup changes the interaction context, or the first expected transition fails. Supply what deterministic code tried and why it failed. A proposed starting budget is one clear attempt plus one obstruction recovery before model control; this is a tuning hypothesis to validate, not an established optimum.
5. Give the model useful actions: inspect a frame, choose an observed control, follow a page-derived link, select an approved auth route, wait for a specific condition, return to the previous context, or hand off to the field planner. Permit multiple steps toward the form, with fresh observation after every step. The deterministic layer validates action targets, approved values, capability flags, and side-effect boundaries.
6. Hand off to deterministic filling only after observing actual application fields in the correct tab/frame. The model can interpret unfamiliar field labels and page options; the approved plan and validators own what can be typed. Read back values and upload state before advancing. A failed fill-page classification must be able to return to the navigation supervisor within the same job.
7. Submit through the existing approved submission path and confirm with independent evidence. Then run the Gmail insider/generate/draft chain for this application, recording no-contacts and saved-but-unverified outcomes accurately. Only then inspect the feed again.

The immediate gap is between URL resolution and form readiness. `runNavigation` returns early for a matched link/captured URL, including login landings. `runAtsLiveFill` uses `advancePastPosting` and can return `FORM_NOT_REACHED` or `UNKNOWN_LANDING` without invoking the navigation sidecar. Post-session triage's `engage_agent_leg` requires a navigation wall, so a fill-stage landing failure may not be eligible for it. Increasing model strength alone cannot fix a decision point the model never receives.

Model configuration should also be explicit by role. The browser-use navigator reads `NAV_AGENT_MODEL`, separately from the TypeScript applier/outreach settings, and defaults to `claude-sonnet-4-6` on its Anthropic path. Triage explicitly requests low effort. Before changing budgets, record the actual provider/model, reasoning setting, context supplied, time to first useful action, and verified outcome. Navigation planning deserves enough reasoning and visual context for the task; cheap fast paths should not silently select a weaker planner.

## How to measure the next implementation

Use fixed synthetic transition cases for known regressions and a separate fresh live cohort. Count verified form reach, verified fill, verified submit, Gmail draft read-back, human interventions per application, repeated unchanged-state actions, model calls/tokens, and wall-clock time. Report live and fixture evidence separately. A model's “done” response, URL resolution, or a completed cycle process is not application success. A target such as “almost every application” needs coverage measurements across ATSes and failure classes; current evidence does not establish it.
